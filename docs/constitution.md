# Constitution

**Status:** Accepted
**Last updated:** 2026-10-29

Non-negotiable principles for jairojobs. Every spec, plan, and PR is measured against this file.
Change it deliberately, via an ADR.

## 1. Stack

| Layer | Choice | Notes |
|---|---|---|
| Language / runtime | Elixir 1.20 / OTP 29 | |
| Web | Phoenix 1.8, LiveView | Server-rendered first; LiveView for interactivity |
| UI | Stock `CoreComponents` + Tailwind v4 + daisyUI | No third-party component library (ADR-0001) |
| Database | PostgreSQL 17 via Ecto; UUID v7 primary keys | (ADR-0002, ADR-0004) |
| Deployment | Fly.io, region Singapore (`sin`) | (ADR-0003) |
| Background jobs | None yet | Evaluate Oban via ADR when a spec needs it |
| Email | Swoosh | Local dev mailbox at `/dev/mailbox` |

## 2. Principles

1. **Simple over clever** — plain Phoenix contexts, LiveView, Ecto. No abstractions until the third use.
2. **Boring technology** — prefer what ships with Phoenix/Elixir/Postgres over adding a dependency. Every new dep needs a one-line justification in the plan.
3. **Server-rendered by default** — LiveView for interactivity; no JS framework. Hand-written JS only via hooks and only when LiveView can't do it.
4. **Mobile-first, always** — design and test at phone widths first; desktop is the enhancement.
5. **Spec before code** — no feature work without an Approved spec and a plan (see `docs/README.md`).
6. **Tests are part of the feature** — a task isn't done until its REQ IDs have tests and the suite is green.
7. **Authorization is explicit** — every query for private data is scoped by the current user/role; never trust an ID from the URL.
8. **Small, reversible steps** — one task = one commit; the suite stays green on every commit; migrations are additive where possible.
9. **Trust the platform's moderation role** — nothing employer-submitted goes public without Admin approval.

## 3. Testing rules

1. **Test pyramid, Phoenix-style**
   - *Context tests* (`test/jairojobs/…`) for business rules — the bulk of tests.
   - *LiveView / controller tests* (`test/jairojobs_web/…`) for each user-facing flow via
     `Phoenix.LiveViewTest` — one happy path plus key failure paths per REQ.
   - *No browser / E2E tests* (Wallaby etc.) for now; revisit if LiveView tests prove insufficient.
2. **Every Gherkin scenario has at least one test** named `REQ-<id>: <scenario name>`:
   `test "REQ-003-2: listing without salary range is rejected"`.
3. **Fixtures via context functions**, not raw `Repo.insert!` —
   `test/support/fixtures/*_fixtures.ex` as generated by `phx.gen.*`.
4. **Authorization tests are mandatory** for any private resource: at least one test proving
   another user *cannot* read or modify it.
5. **Async by default** (`use Jairojobs.DataCase, async: true`); opt out only with a comment
   explaining why.
6. **No sleeps, no flaky retries** — use `assert_receive`, `render_async`, or deterministic setup.
7. **Emails are asserted**, not just sent — `Swoosh.TestAssertions.assert_email_sent/1` for any
   REQ that sends mail.
8. **`mix precommit` must pass before every commit** (compile with warnings-as-errors, format,
   unused-deps check, tests). The alias already exists in `mix.exs`.
9. **CI is the referee** — GitHub Actions runs `mix precommit` on every push and pull request on
   a clean machine; `main` must stay green. Set up in spec 001.
10. **CI runs only for product code** — the workflow is skipped when a push touches only
    non-product paths (`docs/**`, `scratchpad/**`, `*.md`, `.github/**` except the workflow
    itself). Use `paths-ignore` in the workflow; keep that list in sync with this rule.
11. **Coverage** — no numeric threshold; REQ-coverage (rule 2) is the measure that matters.

## 4. Code conventions

1. **Follow `AGENTS.md`** for Phoenix / LiveView / Ecto idioms. It is authoritative; this
   section only adds the project-specific layer.
2. **Contexts are the API** — `JairojobsWeb` never calls `Repo` directly; it calls
   `Jairojobs.Listings.*` etc. Context names come from the glossary in spec 000.
3. **Scope everything** — context functions touching private data take the current scope/user
   as the first argument (`Listings.list_my_listings(scope)`), matching `phx.gen.auth`'s
   `Scope` pattern.
4. **Schemas are thin** — changesets and validations only; business rules live in contexts.
5. **Money** — salary stored as integer **centavos** in PHP, never floats. One display helper.
6. **Time** — store `utc_datetime_usec`; display in `Asia/Manila`. One formatting helper.
7. **Naming** — glossary terms verbatim: `Listing`, `Application`, `Profile`, `Region`.
   No synonyms in code (`Job`, `Post`, `Resume`).
8. **URLs** — slugs for public listing pages; UUIDs only in admin/internal URLs (ADR-0004).
9. **Components** — extend `core_components.ex` or add to `JairojobsWeb.Components.*`;
   no inline Tailwind soup for anything used twice.
10. **Migrations** — one concern per migration; additive; never edit a migration already on `main`.
11. **Commit messages** — Conventional Commits with REQ IDs:
    `feat(listings): require salary range (REQ-003-2)`.
12. **No PII in logs** — never log emails, names, or CV contents; log IDs only.

## 5. What we deliberately do NOT do

- No JavaScript framework (React/Vue/Svelte) or SPA; no GraphQL/REST API until a consumer exists
- No third-party UI component library (ADR-0001)
- No microservices, umbrella apps, or separate admin app — one Phoenix app
- No ORM-style abstractions over Ecto, no "service objects", no repository pattern
- No feature flags, A/B tooling, or analytics SDKs in phase 1
- No background-job library until a spec actually needs one (then evaluate Oban via ADR)
- No soft deletes by default
- No Docker for local development (native Elixir + Homebrew Postgres)
- No premature multi-tenancy or multi-user employer accounts

## 6. How specs are written

- Specs describe **what** and **why**; never **how**.
- User stories in the form: _As a \<persona\>, I want \<goal\>, so that \<benefit\>._
- Every user story has an ID (`US-NNN-n`); every requirement has an ID (`REQ-NNN-n`), a
  `Serves:` line, and Gherkin acceptance scenarios (see `docs/README.md` → Writing style).
- "Out of scope" and "Open questions" sections are mandatory, even if empty.
- A spec must be `Approved` before a plan is written.

## 7. Definition of Done

A task or feature is Done only when all of the following hold:

- [ ] Every REQ in the spec has a passing, REQ-named test
- [ ] Authorization tests present for any private resource
- [ ] `mix precommit` green locally **and** CI green on `main`
- [ ] Works at 375 px width (phone) before desktop
- [ ] No new deps without a justification line in `plan.md`
- [ ] `docs/architecture/` updated if contexts or data model changed
- [ ] `tasks.md` checked off; spec status set to `Done`
- [ ] Deployed to Fly.io (once deployment exists) and smoke-checked
